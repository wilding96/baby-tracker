## 1. 待定项（新会话第一件事）

### 1.1 游戏方向

| 方向 | 是什么 | 与现有资产的复用度 |
| --- | --- | --- |
| **A. 3D 竖版弹幕** | 把现有的 2D 雷电"立体化"：轨道俯视相机、3D 敌机与弹幕、同样的 build 与属性克制 | 最高，机制几乎可以照搬 |
| **B. 3D 追尾射击** | 第三人称跟随相机、锁定目标、滚转闪避，星战/空战味 | 中，操作与关卡要重做 |
| **C. 另起炉灶** | 与射击无关的全新品类 | 低，只有工程骨架可复用 |

**我建议 A**：你现有的手感和数值验证过一遍（卡牌、属性克制、能量曲线、局外养成），3D 化只换表现层，风险最小、最快能看到东西。等 A 跑通，再考虑要不要做 B 当第二条产品线。

### 1.2 还要一起定的事

- **题材**：波普继续，还是换一套？（波普语言在 3D 里同样成立，且低多边形平涂天然契合）
- **平台**：桌面为主，还是手机优先？（决定相机、操作与性能预算）
- **单局时长**：3 分钟还是 10 分钟？
- **是不是新产品线**：和现有的 baby-tracker 仓库是同一个 Next.js 项目（新路由），还是完全独立的新仓库？

## 2. 技术选型

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 渲染 | **Three.js**（裸库）或 **React Three Fiber** | 生态最大、体积可控、文档全。项目已是 React/Next，用 R3F 上手更快；追求极致可控就用裸 Three |
| 不建议 | Babylon.js / PlayCanvas | 功能过剩，包体和心智负担都更大 |
| 物理 | **不要**完整物理引擎。弹幕用自研球体/AABB 检测 | 弹幕要的是确定性，不是真实物理 |
| 构建 | 沿用 Next.js（新路由 `/game/<name>`）或独立 Vite 工程 | 独立工程的首屏更快、迭代更轻，但会多一套部署 |
| 音频 | WebAudio，沿用现有 `useGameAudio` 的思路 | 已有实现可参考 |
| 状态 | **游戏状态一律放引擎里，不进 React** | 见 §9 红线 |

## 3. 架构分层

沿用 2D 改版已经验证过的骨架（同一个目录约定，经验可以直接搬）：

```
src/app/game/<name>/
  page.tsx          React 外壳：菜单 / 结算 / 暂停 / 选择弹层。只处理低频状态
  engine/
    config.ts       所有可调数值集中在这里（数值不要散落在渲染代码里）
    types.ts        类型定义
    pools.ts        对象池
    game.ts         固定步长循环 + 世界状态 + createEngine()
    cards.ts        流派卡
    meta.ts         局外养成与存档
  render/
    scene.ts        每帧绘制（只做 GPU 提交，不做逻辑）
    sprites.ts / assets.ts   资源生成与缓存
```

**关键边界**：`engine/` 里不出现任何 React；`page.tsx` 不出现任何 per-frame 状态。这条边界是 2D 改版性能达标的根本原因。

---

## 4. 性能硬指标（不可让步）

1. 中端设备稳定 60fps
2. 同屏 **400+ 弹幕**不掉帧
3. 每帧 draw call 目标 **< 60**（靠实例化/合批，不是靠减内容）
4. 游戏循环内 **零 GC**（高频实体全走对象池）
5. 纹理/几何显存预算 **< 100MB**
6. 首屏可玩 **< 3s**（本地）

---

## 5. 3D 特有的技术要点

- **美术方向**：低多边形 + 平涂（flat shading）+ 硬边描边。这既省性能，又和波普审美天然契合。不要 PBR 金属感、不要体积光。
- **实例化**：子弹、碎片、小敌机一律 `InstancedMesh`。这是 400+ 弹幕的关键。
- **相机**（方向 A）：正交或弱透视的俯视轨道相机，保持"一眼看清弹幕"的可读性——这是弹幕游戏的命门，不能为了立体感牺牲它。
- **光照**：1 个方向光 + 环境光足矣。阴影只给玩家机，其余关掉。
- **后处理**：先不做。要做也只做描边（OutlinePass），呼应硬边风。
- **分辨率**：`renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`。
- **可读性红线**：3D 化以后，玩家机、敌弹、奖励三者仍必须在一眼之内分清。背景对比度永远低于前景。

## 6. 分阶段里程碑

每个阶段结束时都必须**可玩、可测、可回滚**，不做半成品推进。

| 阶段 | 目标 | 完成标志 |
| --- | --- | --- |
| **M0 骨架** | 空场景 + 一架能动的飞机 + 一个游戏循环 + 帧率读数 | 能在浏览器里开起来，60fps |
| **M1 手感** | 自动开火、敌机、碰撞、扣血、死亡 | 能打死人和被打死 |
| **M2 节奏** | 波次、Boss、难度曲线 | 一局能玩满 3 分钟且难度有起伏 |
| **M3 复玩** | 三选一 build 卡、局外养成、存档 | "再来一局"的理由成立 |
| **M4 打磨** | 美术、音效、动效、移动端适配 | 可以拿给别人玩 |

M0 不要超过一个工作段。骨架跑不通，后面全是空谈。

---

## 7. 每个阶段的验收标准

- `tsc --noEmit` 通过
- **实机**跑出 60fps，并把 FPS / 帧耗时读数贴出来
- console 无报错
- 有一张截图或一段录屏

**没有实测数据就不算完成。**

## 8. 可以直接从 2D 改版搬过来的东西

这些都已经在 `src/app/game/raiden/` 里验证过了：

1. **卡牌系统**：16 张行为卡，分弹幕 / 元素 / 生存 / 经济四流派，每张有独立机制而非纯数值
2. **属性克制**：电 / 火 / 冰三属性，Boss 带弱点与抗性，逼玩家临场调 build
3. **能量条与升级曲线**：`base=100, growth=1.16`
4. **局外养成**：得分换星尘 → 永久强化（生命 / 炸弹 / 能量 / 备用机体）
5. **波普色板与硬边规则**：`#FF2D2D / #E5007E / #FFD400 / #0057FF / #00C2FF / #101010 / #FFF8E7`
6. **对象池写法**（`engine/pools.ts`）
7. **页面外壳的六种相位**：menu / playing / card / revive / pause / gameover
8. **拟声词打击反馈**（POW! / BOOM! / KAPOW!）

## 9. 风险与红线（都是踩过的坑）

1. **不要把游戏状态放进 React state**。2D 版最初每秒 60 次重渲染一个三千多行的组件，是最大的性能问题。
2. **不要用 `shadowBlur`、辉光、全屏模糊**。2D 版有 97 处，是掉帧的头号嫌疑；波普风格本来也不需要。
3. **不要在没有实测的情况下声称"流畅"**。写完必须跑，跑完必须读数。
4. **不要让两个 agent 同时改同一个目录**。本次踩过：两边同时写同一个文件，其中一个被写成 0 字节。
5. **任务书里必须写清"不得删除或覆盖已有文件"**。否则"只允许修改 X 目录"这句话会连带把删除也合法化。
6. **不要为了立体感牺牲弹幕可读性**。3D 最大的诱惑就是用低机位和景深，那会直接毁掉这个品类。

## 10. 与现有项目的关系

- 本仓库现有的 2D 版本（`src/app/game/raiden/`）**保留**，作为 3D 版的机制参考与数值来源。
- 现有独立 demo（`public/game/pop-demo/index.html`）是单文件零依赖的波普竖版弹幕原型，可当作"最简参照实现"。
- 3D 版是**新东西**，不要就地改造 2D 版。
