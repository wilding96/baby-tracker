# 两版战机游戏 —— 最终方向裁决书

日期：2026-10-10（v2，**已用真实截图与实机读数校正**）
对象：`src/app/game/raiden/`（雷电战机）与 `src/app/game/pop3d/`（萌宠战机）
性质：**决策文档**。本文件回答"到底怎么继续"。

> **v2 修订说明**：v1 的诊断（"明度结构缺失 / 前景背景只差 0.06 明度"）是从 3D 版的设计文档
> 反推的，**看到真实画面后判定为错误**。当前默认的纸片渲染器用的是深色场地，弹幕对比度
> 实测"极高"。v1 的美术处方（限定三色）因此也调整了优先级。详见 §2、§4。

## 0. 结论（一句话）

> **以 `pop3d` 的引擎与 three.js 3D 渲染为唯一地基**（3D 是既定目标，且已用样机验证可行），
> 把 `raiden` 降级为零件库（HUD 系统 + 16 张行为卡 + 养成闭环搬过来）。
> 3D 的形态是 **「平面世界 + 立体实物」**：场地用**正交投影**（平面、无透视、判定点 1:1），
> 只有战机 / 敌机 / 子弹 / 障碍是立体模型。美术上不是"换风格"，
> 而是**把被关掉的立体线索逐条打开**（强方向光 / 墨黑描边 / 偏移贴地投影 / 姿态旋转 / 厚度）。

**v3 修订（2026-10-10 晚）**：v2 曾建议"three.js 降级为演出工具、战场回到 2D"。
该建议**与项目目标冲突，已作废**。

**v4 修订**：v3 曾按"透视相机 + 可延伸的 3D 客厅"做样机，方向错了——
那是"3D 场景"，不是"平面世界 + 立体实物"。已在 §4.5 重写。

## 2. 修正后的诊断

### 2.1 v1 错在哪

v1 说"明度结构缺失，前景背景只差 0.06"——**这是 3D 渲染器的问题，而 3D 已经不是主路径了。**
实测当前默认的纸片渲染器：深蓝场地 + 亮红带黑描边的弹幕，512 颗同屏仍"对比度极高，
看得非常清楚"。**配色不是问题，不需要换色板。**

### 2.2 "无聊"的真正来源：三件事

**① 战场是"空舞台"，不是"地方"。**

pop3d 背景 = 纯色深蓝 + 0.08 网点 + 3 条斜色带。代码里甚至写明了取舍：

> "背景装饰一律用'大件'：小圆点会和子弹混（可读性红线），所以不用星野"

可读性红线被允许把环境**剥空**了。结果是：正确、清楚、但情绪上是空的。
raiden 同理（米白场地 + 极淡网点）。弹幕游戏**必须**留出弹幕可读性，但"干净"和"空"
是两件事——现在的做法把两者混为一谈。

**② 题材没有被戏剧化。**

`萌宠战机` 的全部钩子是"猫玩具"：✨激光笔 / 🐟小鱼干 / 🦴骨头。你自己的风格板 C
画的就是**一只黑猫剪影射出绿色激光，周围是鱼和骨头的黑色剪影**——题材感极强。
但真实游戏里，这个钩子只体现为：(a) 三种武器颜色，(b) 一张"猫坐火箭"的玩家机贴图。
**题材的世界没有建起来。**

**③ 玩家与敌人不同族。**

实测贴图：玩家 = 一只有表情、有座舱、有故事感的卡通猫（具象角色）；
敌人 = 抽象几何色块（品红/黑/白的倒三角）。**一个"角色"和一个"符号"不该出现在同一张画里。**

不是拼凑的。** 这就是你觉得"第一个的界面 UI 挺好"的原因，而且这个判断是对的。

## 4. 美术方向（v4 修订版）

> **3D 形态见 §4.5：这是本文件最重要的一节。**

**不动配色。** 改三件事，按收益排序：

### 第一优先：把战场变成"地方"

给场地一个具体的所处空间，用**大幅、低对比、绝不可能是子弹**的形体：

- 从上方俯视的**客厅地板 / 沙发 / 地毯**，或一整只**巨大的猫爪**
- 尺度必须"大到不可能被误认成子弹"（沿用现有"只用大件"的规则，但**要用满**）
- 环境层永远比弹幕低一档明度与饱和度

这一条是"无聊"的头号解药，而且是**零每帧成本**的大色块。

### 第二优先：把玩具变成世界

敌人不该是抽象三角，应该是**主人的其它玩具 / 家里的物件**：
发条老鼠、拖鞋、扫地机器人、卷纸、毛线球。收益：

- 题材一秒可读（不用看说明就知道"我是猫，我在打这些东西"）
- **"打哪里"白送**：发条 = 弱点、电池仓 = 暴击点

### 第三优先：~~黑墨剪影 + 彩色光束~~ → **已用样机证伪，改为「亮色玩具 + 玩家侧唯一彩色」**

> **样机结论（2026-10-10，见 `docs/superpowers/art/battlefield-mockup.html`）**：
> 「敌机一律墨黑剪影」试了三版（v1/v2/v3）都没通过灰度验收，原因是结构性的：
> **黑剪影在暗底上必须靠纸白描边才看得见（否则消失），而纸白描边和「奖励 / 弹体」
> 抢同一条明度带；而且满屏白线稿会把弹幕的注意力抢走。**
> 换来的画面是"涂鸦线稿"，弹幕反而最不显眼。
>
> **因此这条建议作废。** 敌机改回「亮色实心 + 墨黑描边」（两款原游戏验证过的做法），
> 独特性改由**题材 + 环境 + 玩家侧配色**承担。

| 角色 | 处理 | 灰度带 |
| --- | --- | --- |
| 玩家（绿猫） | **画面里唯一的绿**，光束是唯一带白芯的东西 | 0.63 / 芯 0.97 |
| 敌机（玩具） | 亮品红实心 + 墨黑描边（**不是**黑剪影） | 0.33 |
| 敌弹 | 亮红/品红实心 + 小纸白芯 + 墨黑边 | 0.42 |
| 奖励 | **黄**（纸白会和敌机描边、弹芯撞带） | 0.79 |
| 环境 | 只允许大色块 + 长直线 | 0.11~0.19 |
| 危险标记 | 精英/炮台用**红**强调（红 = 敌弹 = 危险，一套语义） | 0.42 |

### 第三优先（替代版）：环境里**不许出现中小图形**

样机 v3 在地毯上画了同心圆环 + 木纹 + 电线，反馈立刻变成
"大量散落的灰色小圆点…分不清哪些是背景装饰，哪些是弹幕"。
这是既有那条老规则的翻版（"小圆点会和子弹混"），环境里任何
中小尺寸、中等对比的图形都会被读成弹幕。**环境只允许大色块和长直线。**

### 关于验收标准的一次修正

样机证明：**"转成灰度后仍能一眼分清 玩家 / 敌弹 / 奖励"这个标准太严，而且方向不对。**
弹幕的可读性很大程度来自**颜色 + 运动 + 图案结构**，不是明度。硬把弹幕塞进明度带，
会逼它和奖励、敌机抢同一条带——样机 v2→v4 三次撞的都是这面墙。

**修正后的验收标准（3 条）：**

1. 灰度下必须分清 **玩家 / 敌方实体 / 玩家侧有利物**（这条能过，且必须过）
2. 弹幕在**彩色 + 运动**下必须一眼可读（用实机跑，不用灰度图）
3. 环境层任何元素都不得被误认成弹幕或奖励

## 4.5 3D 的正确形态：**平面世界 + 立体实物**（v4 修订）

样机：`docs/superpowers/art/battlefield-3d-mockup.html`（需本地静态服务器，ESM + importmap）。

### 先说清楚要的是哪一种 3D

> **场地是一张平面**（正交投影，没有透视、没有近大远小，判定点 1:1 映射），
> **只有战机 / 敌机 / 子弹 / 障碍是立体实物。**
> 参照系：Qute《Ginga Force》《Eschatos》、Raiden V 那一类。

**不要**做成一整个带透视的 3D 场景（相机推近、近大远小、可延伸的地板）。
两者是完全不同的东西，样机 v1 做错的就是后者。

### 正交带来的好处（玩法上更优）

- **没有近大远小** → 远端敌机和近端敌机一样大，**判定天然公平**；
  也顺手解决了"近端敌人显得比玩家大"的尺寸竞争问题
- 场地是平面 → 判定点 1:1 映射，不需要为透视做位置补偿

### 正交带来的代价，以及立体感由什么承担

"透视"这条最强的深度线索基本被关掉了。**立体感改由这 5 条承担（样机已验证）：**

| # | 做法 | 说明 |
| --- | --- | --- |
| ① | **强方向性光照** | 受光面 / 顶面 / 背光面落在**三个不同明度**。环境光 0.5 + 主光 1.55（左上前方）+ 冷补光 0.45 + 背光 0.3。**不要**再用环境光 1.05 + 主光 1.7 把顶面曝成一个值 |
| ② | **墨黑描边 = 反向外壳** | `BackSide` + 放大 7.5%，3D 模型直接长出硬边线稿，和波普身份接上。只给玩具/Boss/玩家，**不给子弹**（会把小弹体糊掉） |
| ③ | **贴地投影按高度偏移** | 单一光源方向全场一致（光在左上 → 影子朝右下，偏移 ∝ 离地高度）。平面上的影子一偏，"悬在地面上"立刻成立。**这是正交弹幕里最有效的一条** |
| ④ | **姿态旋转 = yaw / pitch，不是 roll** | **俯视视角下 roll 几乎看不见**；真正看得见的是**偏航与俯仰**。所以立体感最强的读法是：**物体转向 → 你从不同角度看到它的不同侧面**。发条玩具本来就在原地绕圈，这条和题材天然吻合。静止截图验证不了，**必须做成会动的版本**（已做，见下） |
| ⑤ | **厚度与倒角** | 正交会吃掉纵深，扁盒子看起来就是扁的。实体必须有可见厚度 |

### ⚠️ 性能红线：这套视觉必须配实例化，否则 DC 爆掉

**已实测，改造前后对照（同一台机器、同一套造型，只改架构）：**

| 版本 | 弹幕 | draw call | 三角形 | fps（无头 Chrome） |
| --- | --- | --- | --- | --- |
| v3 朴素实现 | 71 | **271** | — | 41 |
| v4 实例化 + 顶点色合并 | 71 | **30** | 32.8k | 48 |
| v4 实例化 + 顶点色合并 | **426** | **30** | 40.9k | 40 |

**结论：draw call 从 271 → 30（降 9 倍），而且弹幕从 71 涨到 426（6 倍）时 DC 一点没变。**
这正是实例化的意义：**DC 与弹幕数量脱钩**。423 颗弹幕只多花了 8 帧。

> **注意读数的可信范围**：这是无头 Chrome（`--disable-gpu`，软件光栅化），
> **绝对 fps 不代表真机**。可移植的结论是 **DC=30 / tris≈33~41k**；
> 真机 fps 必须按 §7 的口径在真实设备上复测。剩余那 40fps 的天花板是
> 全屏软件光栅 + MSAA 的固定成本，不是弹幕造成的（弹幕翻 6 倍只掉 8 帧）。

**落进预算的四条手法（前三条是 §5 原本就写明的要求，v3 违反了它）：**

| 对象 | 做法 | DC |
| --- | --- | --- |
| 弹幕 | 每种弹型 `InstancedMesh`，本体 + 高光**合并成一个带顶点色的几何体** | 3 种 = **3** |
| 所有贴地投影 | **一个** `InstancedMesh`（`count` 每帧改，上限 200） | **1** |
| 敌机 / 玩具 | 每个预制体先把所有 primitive **合并成一个带顶点色的几何体**（+ 一份合并的描边几何体），再按类型实例化 | **12** |
| 玩家 + 僚机 | 同上（僚机 2 架共用一份几何体） | **4** |
| 场地 + 合并后的分格边框 + 光束/落点 | — | **9** |
| **合计** | | **30** ✔（红线 <60） |

**关键手法：**
1. **顶点色代替多材质**——否则一个玩具要拆成 5~8 个 DC
2. **反向外壳描边也要合并 + 实例化**，不能每个 primitive 挂一个
3. **弹珠要减面**：`Sphere(0.66,14,10)` 单颗约 **412 面**，426 颗 = **17.5 万面**
   去画只占几十像素的小球。降到 `Sphere(6,5)` + 八面体高光 ≈ **56 面/颗**，
   总面数 18 万 → 4.1 万，fps 35 → 40。
4. **`mergeGeometries` 混用「索引几何」和「非索引几何」会返回 null**，然后在
   render 里炸 `reading 'id' of null`（pop3d 自己文档里记过这条雷）。
   `Icosahedron/Octahedron` 是非索引、`Box/Sphere/Cylinder` 是索引
   → 每块几何先 `toNonIndexed()`，并把属性集统一成 `position/normal/color`。



### 风格命题

> **世界是一张"印出来的画"，角色是摆在上面的立体实物。**

场地用印刷网点（Ben-Day）+ 粗黑分格 + **平行板缝**（正交下板缝永远平行、不收敛，
一眼就是"印的"），而不是有透视的地板。样机里用的就是这套。

### 样机实测

**静止态（v2）**

- 视觉复核：**"整体是俯视的平面视角，没有明显的近大远小的透视变形"**，
  同时**"通过阴影和角色设计营造出了很强的立体感"**、
  **"所有角色下方都带有明显的深色椭圆形阴影，赋予它们悬浮在地面上的空间感"**、
  **"圆润的体积感"**。
- 子弹被读成"大量的红色小球"（3D 珠子语言成立）；玩家定位环（贴地白环）被正确读到。
- 6 种玩具全部可辨（毛绒熊 Boss / 发条机械鼠 / 尖叫鸭 / 拖鞋 / 毛线球 / 扫地机器人）。

**动态态（v3，带 `?t=` 确定性单帧）**

- 实时跑通：`t=11.5s`，console 零报错。
- **yaw 立体线索成立**：同一帧内，视觉模型对同一批敌机分别报出
  "面朝左下 / 面朝右侧 / 面朝左侧"；换到另一帧变成"朝左上 / 朝右下 / 朝左下"。
  —— 也就是说它看出**同一个模型处在不同朝向上**，这正是"转向 → 看到不同侧面 → 感知体积"。
- 老鼠的尾巴被正确读到（"尾巴卷曲"）。
- **代价见上面的「性能红线」：DC=271。**

### 样机跑通过程中抓到的坑

1. **坐标方向**：相机在 +z 侧 → **z 越小越远（屏幕上方）**。样机 v1 把玩家放在远端、
   Boss 放在近端，结果玩家跑到画面顶部、Boss 跑到画面底部。
2. **相机不建议改**：pop3d 原本的 `正交 + 俯角 16°` 方向是对的。
   样机用 24° 是为了让玩具的受光/背光面拉开一点；两者都在合理区间。
   **"无聊"不是俯角造成的，是 ①~⑤ 全都没做。**
3. **我把 roll 说错了**：v2 写"横移侧倾"，俯视下 roll 看不见，已改为 yaw / pitch（见 ④）。
4. **DC 预算**：必须实例化 + 顶点色合并（见上）。

### 俯视剪影的五条规律（这一轮的实测产出）

俯视视角下**只有剪影在说话**。以下五条全部是踩过才知道的：

| # | 规律 | 反面教材（我踩过的） |
| --- | --- | --- |
| ① | **扁圆盘（DISC）代替球** | 球从正上方看就是一团模糊的包；盘才是明确的圆。耳朵/眼睛/脚/鼻头一律用盘 |
| ② | **附件必须超出母体轮廓，且高度不低于母体顶部** | 耳朵放在 y=1.05、头顶在 1.40 → **实际只露出 0.125**，完全读不出来。算一遍就知道为什么"没有耳朵" |
| ③ | **"尖"必须用 3 段锥** | `ConeGeometry(r,h,4)` 的俯视剪影是**正方形**；扁三角柱虽是三角形但"立不起来"；只有 **3 段锥**既俯视是三角、又能高过轮廓 |
| ④ | **不要用整圈圆环做机械特征** | 整圈红环必然被读成"黑白同心圆图案"。改成**指向前方的三角 + 前保险杠 + 伸出的滚刷** |
| ⑤ | **细节不能和主体剪影抢辨识度** | 把发条做成"凸起的大环 + 横杆"→ 整只老鼠被读成"粉色小猪、白色面部"。退回一个小旋钮后恢复正常 |

### ⚠️ 最重要的发现：**屏幕上只有 40px 时，物种辨识度不可能成立**

同一张截图：

| 看法 | 玩家（绿猫）被读成 | 敌机（发条鼠）被读成 |
| --- | --- | --- |
| 整幅图（角色约 40~60px） | 青蛙 / 鳄鱼 / 小狮子（**多次不稳定**） | 粉色小章鱼 / 小蝙蝠 |
| **裁出来放大 3 倍** | **"最像是一只猫……两只尖耳朵、三角形、有尾巴、四个脚掌，非常像猫"** | **"非常像老鼠"** |

**结论：造型是对的，误读是显示尺寸造成的。** 因此：

1. **战场尺度下的目标不是"看得出是猫"，而是"一眼认出是玩家"** ——
   靠的是**颜色独占（唯一的绿）+ 贴地定位环 + 绿光束**，不是物种细节。
2. **物种辨识度应该放在大尺寸出现的场合**：菜单立绘、Boss、图鉴、结算界面。
3. **不要继续在战场尺度上抠物种细节**——投入产出已经不划算（这一轮为耳朵反复了三遍）。

> 复盘：一轮里做对的一件事是**改用"裁图放大再问"来做客观验证**。
> 整幅图的物种判断噪声极大（同一模型对同一角色给出三种答案），
> 放大后判断才稳定。**以后凡是要判"造型读不读得出来"，都必须放大后再判。**



### 仍未解决（按修正后的优先级）

1. **画面偏暗**：受光/背光的明度差还可以再拉大。**这是现在最影响"好不好看"的一条。**
2. **真机 fps 未测**：DC 与面数已达标（30 / ~41k），但无头软件光栅的数字
   不代表真机，必须按 §7 在真实设备上复测。
3. **"玩家"的辨识度可以再加强**：现在靠"唯一的绿 + 贴地定位环 + 绿光束"。
   可以考虑再加一层构型差异（只有玩家带白光 / 只有玩家有环）。
4. **物种辨识度交给大尺寸场合**：菜单立绘、图鉴、结算、Boss 入场。
   **不在战场尺度继续抠**（见上）。
5. 移动端实测（沿用现有：`(pointer: coarse)` 关 bloom / 降 DPR）。
6. 剩余小瑕疵：拖鞋的 V 形鞋带在灰度下仍可能被读成分区色块；
   毛线球被读成"条纹球"（可接受，毛线球本来就是缠绕的）。

### 明确不做

- **不要透视相机 + 可延伸的 3D 环境**（那就变成"3D 场景"了，不是这个方向）。
- **不要为了立体感压低机位或加景深**（§9 红线 6 仍成立：弹幕可读性 > 立体感）。
- **不要恢复 shadow map**：偏移贴地投影更便宜，也更贴硬边风格。

## 5. 耐玩性

### P0（加法，不改架构）

1. **擦弹（graze）**：贴近敌弹给倍率。判定全是球体距离，加一个外圈环即可

### P1（结构性）

### 第 2 步：静态战场样机 —— **已完成**

产出：`docs/superpowers/art/battlefield-mockup.html`（零依赖单文件，`?gray=1` 出灰度图）。
截图证据：`.dsh-shots/MK*-color.png` / `MK*-gray.png`（5 轮迭代）。

五轮迭代的收获（**全部是在写任何游戏代码之前，用截图换来的**）：

| 迭代 | 反馈原话 | 改了什么 |
| --- | --- | --- |
| v1 | 弹芯墨点在灰度下变甜甜圈，被读成"飘浮的几何小物件" | 弹体改实心 |
| v1 | 老鼠剪影被读成"黑白猫头" | 重画剪影（尖吻 + 圆耳 + 胡须 + 显眼发条） |
| v2 | 内部纸白高光把实心弹打散成"碎片" | 去掉内部亮斑 |
| v3 | "地毯圆环 + 木纹 + 电线"和环形弹撞车，**分不清哪些是背景装饰** | 环境只留大色块 + 长直线 |
| v3 | 黑色方块 + 粗字母 = 天然像「道具图标」，被读成奖励 | 换掉该敌人（形状语言问题，非明度问题） |
| v1~v3 | 黑剪影必须配白描边才看得见，而白描边又和奖励/弹芯撞带 | **「敌机一律黑剪影」作废** |

**样机的最终结论**：可读性的解法会收敛到和现有两款游戏同一套（暗底 + 亮色实体 +
亮色弹幕 + 黄色奖励）——**这不是失败，这正说明差异化的空间不在明度结构，而在
题材、环境、玩家侧配色。** 而"无聊"恰恰就在这三处（§2.2）。

验收标准见 §4 末尾（已从"灰度四分"修正为"灰度三分 + 彩色运动下可读"）。

### 第 3 步：接进 pop3d 引擎 —— **已完成（2026-10-10）**

新增 **`src/app/game/pop3d/render/toy.ts`**，与 `scene.ts` / `paper.ts` **并行**的第三套渲染器，
实现同一个 `Renderer` 接口，挂在 **`?theme=toy`** 后面。引擎 / 数值 / 波次 / 卡牌 / Boss **零改动**，
